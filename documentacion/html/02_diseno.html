1. Objetivos del diseño

El presente documento especifica el diseño del sistema Flora Elegante a partir del análisis aprobado. Define la arquitectura de software, la organización de los componentes, el diseño de la base de datos, el contrato de la API, el diseño de la interfaz de usuario, el diseño del chatbot, el diseño del reporte mensual, el diseño del CRM con protección de datos y las decisiones de seguridad. El nivel de detalle corresponde a un diseño de ingeniería: suficiente para que un equipo de desarrollo implemente, pruebe y despliegue el sistema sin ambigüedades.

2. Arquitectura del sistema

2.1 Estilo arquitectónico

Se adopta una arquitectura en tres capas (presentación, lógica/negocio y datos) con un patrón de controlador frontal (front controller) en la capa de negocio. Las capas se comunican mediante HTTP/JSON (fetch desde el navegador hacia la API PHP) y PDO (PHP hacia MySQL). Esta arquitectura permite: separación de responsabilidades, mantenibilidad por módulo, pruebas por capa y la migración futura a otros backends (p. ej. Node.js o Laravel con PostgreSQL) sin rediseñar la presentación.

2.2 Diagrama de arquitectura (descripción formal)

El diagrama de arquitectura se mantiene como artefacto PlantUML en el repositorio (diagrams/diagrama_arquitectura.puml). Los componentes y sus relaciones son:

2.3 Flujo de una petición

Ejemplo típico: el cliente confirma el carrito. 1) cart.js construye el payload {items:[{id,qty}]} y llama API.savePedido. 2) api.js ejecuta fetch a api/index.php?resource=orders&action=create con método POST y credenciales same-origin (la cookie de sesión fe_session viaja automáticamente). 3) El front controller incluye orders.php. 4) helpers.php autentica la sesión (require_auth). 5) orders.php abre transacción, valida stock con SELECT ... FOR UPDATE, inserta pedido y detalle, actualiza stock y confirma. 6) Se responde JSON {ok, pedido}. 7) cart.js limpia el carrito y muestra la confirmación.

3. Diseño de componentes (backend)

3.1 Controlador frontal (api/index.php)

Lee el parámetro resource, inicia sesión con session_name('fe_session'), configura cabeceras CORS y mapa de rutas {auth, products, categories, orders, dashboard, clientes, interactions}, e incluye el controlador correspondiente. Respuesta 404 JSON para recursos desconocidos. Configuración endurecida: declare(strict_types=1), display_errors=0 y log_errors=1 para no corromper las respuestas JSON.

3.2 Controlador de autenticación (api/auth.php)

Acciones: login, register, me, logout, profile, update_perfil, update_password. Diseño clave: login consulta por correo y activo=1 y verifica con password_verify; register valida formato y política de contraseñas, previene duplicados (409) e inserta usuario + perfil clasificado; update_perfil usa INSERT ... ON DUPLICATE KEY UPDATE para crear/actualizar el perfil sin eliminar datos; logout limpia sesión y expira cookie; update_password revalida la política y actualiza el hash.

3.3 Controlador de productos (api/products.php)

Acciones: list (público, solo activos, con nombre de categoría), adminList (todos, solo administrador), create, update, update_stock, delete (todas restringidas al rol administrador con require_auth(true)). Normalización del estado a 'activo'|'inactivo' y del stock a entero no negativo.

3.4 Controlador de pedidos (api/orders.php)

Acciones: create (cliente), list (cliente), adminList (admin), updateEstado (admin). El diseño transaccional del create es el punto crítico: beginTransaction, SELECT ... FOR UPDATE por producto (evita condiciones de carrera), verificación de stock, inserción de pedido y detalle, UPDATE de stock y commit; cualquier error revierte (rollBack). updateEstado valida la lista blanca de estados.

3.5 Controlador de dashboard (api/dashboard.php)

Calcula con consultas SQL agregadas: total de usuarios clientes, productos totales y activos, pedidos totales, productos con stock ≤ 5 (umbral) y activos, conteo por estado y últimos 5 pedidos con cliente. Solo administrador.

3.6 Controlador de clientes (api/clientes.php)

Consulta los clientes con su perfil; por diseño de privacidad, la consulta SQL selecciona explícitamente nombre, correo, fecha de registro, teléfono, dirección, fecha de nacimiento y preferencias, pero excluye identificacion y metodo_pago (nunca se seleccionan). Solo administrador.

3.7 Controlador de interacciones (api/interactions.php)

Acciones: list (admin), save (público). save normaliza la calificación a 1-5 (null si está fuera de rango) y la sugerencia a texto o null; vincula usuario_id solo si hay sesión (usuario_actual). Es la fuente de datos del reporte mensual.

3.8 Capa de infraestructura (config, db, helpers, bootstrap)

ArchivoDiseño
api/config.phpConstantes DB_HOST='localhost', DB_NAME='flora_elegante', DB_USER='root', DB_PASS='', DB_CHARSET='utf8mb4'. Concentra la configuración para mantenibilidad (RNF-MAN-02).

5. Diseño de la API (contrato de endpoints)

5.1 Convenciones

  • Base URL: api/index.php (mismo origen). Formato: ?resource=<recurso>&action=<acción>.
  • Métodos: GET para consultas, POST para operaciones. Formato de entrada: body JSON (Content-Type: application/json).
  • Formato de salida: JSON {ok: true|false, ...} con códigos HTTP semánticos (200, 400, 401, 403, 404, 409).

7. Diseño del chatbot

7.1 Estructura del módulo (js/chatbot.js)

El chatbot se implementa como módulo IIFE Chat con estado interno chatState (isOpen, phase, messageCount, currentRating, lastProduct, carouselPage, carouselVisited). Utiliza datos del catálogo (Data.productos), textos bilingües (I18n.te) y el carrito (Cart). Expone a window: ChatAsk (enviar texto), ShowMoreArrangements (paginar carrusel), handleRating (seleccionar estrellas) y handleSuggestion (registrar interacción).

7.3 Secuencia de registro de interacción

Tras la calificación y sugerencia, chatbot.js ejecuta API.saveInteraccion, que invoca interactions/save. El backend inserta la fila con usuario_id (si hay sesión) o NULL, canal 'chatbot', y los valores normalizados. El usuario recibe toast "Calificación y sugerencia registradas". Esta interacción queda disponible para el reporte mensual.

8. Diseño del reporte mensual

8.1 Procesamiento en el frontend (js/report.js)

El módulo Report: (1) construye el selector con los últimos 12 meses (valor YYYY-MM) y nombres localizados; (2) obtiene las interacciones con API.getInteracciones (fecha normalizada a YYYY-MM-DD); (3) filtra por prefijo del mes; (4) renderiza métricas con animateCounter (respetando prefers-reduced-motion); (5) renderiza barras de distribución con ancho ≥ 8%; (6) renderiza la lista de sugerencias con estrellas ★; y (7) ejecuta renderRecommendations con las 11 reglas documentadas en el análisis.

8.2 Casos de borde diseñados

  • Mes sin interacciones → bloque "reportEmpty" con mensaje de estado vacío (no mostrar ceros).
  • Rege-ración automática al cambiar de mes si el reporte ya está visible.
  • Contadores decimales para el promedio (1 decimal) y enteros con sufijo % para satisfacción.
  • Distribución recalcula conteos 1..5 y colores por severidad (#c9584d a #3d7a54).

9. Diseño del CRM y protección de datos

El CRM (dentro de report.js) consume api/clientes.php, que por diseño excluye identificacion y metodo_pago. La UI: calcula la edad desde fecha_nacimiento (función calcularEdad con límite 0..129), oculta o revela teléfono/dirección según mostrarSemiprivados, y muestra el marcador «Protegido» (candado) para preferencias, identificación y pago. Los encabezados llevan chips de clasificación (PÚB/SEM/SEN). Este diseño garantiza la regla RN-14/15/16 en dos capas de defensa: backend (no envía) y frontend (no renderiza).

11. Diseño de internacionalización y moneda

El módulo i18n.js mantiene un diccionario TEXTO (claves ES → EN), funciones lang()/moneda() que persisten en localStorage (fe_lang, fe_moneda), función te(es, en) para seleccionar idioma, función precio(cop) que formatea en COP (es-CO) o USD (tipo de cambio RATE=4000), y aplicación de atributos data-i18n al DOM al cambiar idioma. Eventos de dominio fe:idioma y fe:moneda notifican a los módulos (catalog, cart, historial, report, chatbot) para re-renderizar sin recargar la página.

14. Análisis de impacto del diseño sobre los requerimientos

El diseño cubre el 100% de los requerimientos «Must» y «Should». Los puntos sensibles verificados: el enmascarado de datos (RF-PRI y RF-CRM) se garantiza en dos capas; la atomicidad del pedido (RF-CAR-04/05) se garantiza con transacciones y bloqueo de filas; el reporte mensual (RF-REP-01 a 08) se materializa en report.js con la máquina de reglas documentada; el chatbot (RF-CHAT-01 a 13) cubre carrito, catálogo, ocasiones y registro de interacciones. La matriz de trazabilidad de diseño se presenta en el siguiente documento de desarrollo y en el plan de pruebas.
