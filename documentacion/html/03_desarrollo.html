1. Objetivo y alcance del desarrollo

Este documento describe la fase de Desarrollo del sistema Flora Elegante: las convenciones de codificación, la preparación del entorno, la construcción por módulos de backend y frontend, la implementación del chatbot, del reporte mensual y de la seguridad, y las prácticas de calidad y control de versiones aplicadas. El objetivo es dejar constancia de cómo se construyó el sistema a partir de los modelos de análisis y diseño, de manera que sea reproducible, mantenible y auditable.

2.2 Estándares aplicados

  • Nombrado: archivos en minúsculas con separación por guion bajo (camelCase en funciones); constantes de BD en MAYÚSCULAS (DB_HOST...); IDs/funciones de DOM en español descriptivo.
  • Módulos JS: patrón IIFE (const Modulo = (() => {... return {init}; })()); cada módulo expone únicamente lo necesario (encapsulamiento).
  • Separación de capas: ningún archivo JS accede directamente a la base de datos; todo pasa por api.js. Ningún archivo PHP genera HTML; solo JSON.
  • Comentarios: cabecera por archivo con propósito y responsabilidad; comentarios de sección y de decisiones no triviales (p. ej., FOR UPDATE, normalización de tildes).
  • Seguridad por defecto: sentencias preparadas en toda consulta dinámica; salida de datos por texto (textContent) para mitigar XSS; validación en cliente y en servidor (defensa en profundidad).
  • Idempotencia: scripts SQL y bootstrap ejecutables repetidamente sin romper datos (INSERT IGNORE / ON DUPLICATE KEY UPDATE / IF NOT EXISTS).
  • Sin credenciales reales: config.php usa usuario root sin contraseña (entorno de desarrollo); se documenta la precaución para producción.

3. Preparación del entorno de desarrollo

3.1 Instalación del entorno

  1. Instalación de XAMPP con Apache y MySQL activos.
  2. Creación de la base de datos flora_elegante con cotejamiento utf8mb4_unicode_ci en phpMyAdmin.
  3. Importación de sql/flora_elegante_mysql.sql (esquema + datos semilla).
  4. Copia del proyecto a C:\xampp\htdocs\flora-elegante\.
  5. Acceso desde http://localhost/flora-elegante/index.html.
  6. Validación del bootstrap automático: la primera invocación de auth crea roles, usuarios demo y pedidos de ejemplo.

3.2 Decisiones de configuración

  • api/config.php centraliza las constantes de conexión (DB_HOST, DB_NAME, DB_USER, DB_PASS, DB_CHARSET).
  • api/db.php expone db() como singleton PDO; el modo de error es excepción y el modo de fetch es asociativo; EMULATE_PREPARES=false fuerza la preparación real en el servidor.
  • El frontend resuelve la URL de la API con new URL('api/index.php', document.baseURI) para funcionar desde cualquier carpeta de htdocs.

4. Desarrollo del backend

4.1 Capa de infraestructura

4.2 Módulo de autenticación (api/auth.php)

Se implementaron siete acciones:

  • login: SELECT de usuario con rol por correo y activo=1; password_verify; actualización de ultimo_acceso; creación de $_SESSION['usuario'] con id, nombre, email y rol.
  • register: validaciones (campos obligatorios, FILTER_VALIDATE_EMAIL, política de contraseñas con expresiones regulares /[A-Z]/, /[a-z]/, /\d/ y longitud ≥ 8); detección de duplicados (409); inserción de usuario + cliente_perfil; inicio de sesión automático del nuevo cliente.
  • me: retorna el usuario de la sesión actual.
  • logout: limpia sesión, expira la cookie (time -42000) y destruye la sesión.
  • profile: consulta del perfil del cliente autenticado (incluye metodo_pago solo para el titular, no para otros usuarios).
  • update_perfil: actualiza nombre y usa INSERT ... ON DUPLICATE KEY UPDATE para crear/actualizar el perfil sin destruir datos previos; las columnas sensibles se actualizan pero jamás se exponen en el CRM.
  • update_password: valida nuevamente la política y re-hashea la contraseña.

4.3 Módulo de productos (api/products.php)

CRUD con distinción público/admin: list (solo activos, JOIN con categoría), adminList (todos), create (valida nombre obligatorio), update, update_stock (máximo con 0) y delete (baja física). Todas las acciones de administración se protegen con require_auth(true).

4.4 Módulo de pedidos (api/orders.php)

El punto central del desarrollo es la transacción de crear pedido. Implementación:

  1. require_auth (solo cliente).
  2. Validación de items y cantidades positivas.
  3. beginTransaction.
  4. Por cada ítem: SELECT id, precio, stock FROM producto WHERE id = ? FOR UPDATE (bloqueo de fila), validación de stock (rollback + error si insuficiente), acumulación del total y registro del producto.
  5. INSERT de pedido (estado Confirmado, total) y recuperación del id.
  6. INSERT de pedido_detalle y UPDATE stock = stock - cantidad.
  7. commit; en Throwable se revierte si hay transacción activa.

list retorna los pedidos del cliente con su detalle; adminList retorna todos con datos del cliente (nombre, correo); updateEstado valida la lista blanca {Confirmado, En camino, Entregado, Cancelado}.

4.5 Módulo de dashboard (api/dashboard.php)

Consulta agregadas con COUNT y GROUP BY; fetches de productos con stock ≤ 5 y últimos 5 pedidos. Salida JSON con las claves: usuarios, productos_total, productos_activos, pedidos_total, inventario_bajo, umbral_inventario, estados, ultimos_pedidos.

4.6 Módulo de clientes (api/clientes.php)

Consulta SELECT explícita que no incluye identificacion ni metodo_pago. Retorna nombre, correo, fecha de registro, teléfono, dirección, fecha de nacimiento y preferencias. La fecha de nacimiento se entrega para calcular la edad en el cliente; la UI nunca la muestra cruda. Protegido con require_auth(true).

4.7 Módulo de interacciones (api/interactions.php)

list (admin) devuelve todas las interacciones; save inserta interacción con canal 'chatbot', calificación normalizada (1-5 o null) y sugerencia (texto o null), vinculando usuario_id solo si hay sesión activa.

5. Desarrollo del frontend

5.1 Páginas HTML

  • index.html: sitio público con secciones hero, nosotros, catálogo (contenedor renderizado por catalog.js), formulario de registro/perfil (form.js), aviso de privacidad, pie de página, controles de idioma/moneda y el widget de chat.

  • cliente.html: vista del cliente con historial, saludo personalizado y acceso al formulario de perfil.
  • admin.html: panel con secciones de dashboard, productos, pedidos, reporte y CRM; controles de idioma/moneda; botón de cierre de sesión.

5.3 Chatbot «Flora» (js/chatbot.js)

6 fases y estado por conversación. Desarrollo destacado:

  • Normalización: función norm() con toLowerCase + normalize('NFD') eliminando marcas diacríticas.
  • Reconocimiento: findProducto() compara nombre ES/EN y cae en coincidencia por palabras > 3 letras.
  • Orden de intenciones: carrito → producto → afirmación sobre lastProduct (regex de "sí/dale/agrégalo/yes/add it") → 7 ocasiones (regex ES/EN) → más arreglos → catálogo → fin de conversación (solo si mensaje corto y tras al menos 2 mensajes) → saludo repetido → botResponses → defaultResp.
  • Base de conocimientos: Data.botResponses con 20+ entradas bilingües y formatPrecio dinámico.
  • Carrito desde el chat: Cart.add(id) y Cart.totalCOP() dentro de las respuestas; botones con onclick que exponen funciones al window.
  • Calificación: showRatingUI genera 5 .star-btn con aria-label; resaltado acumulativo; window.handleRating guarda currentRating, muestra mensaje según umbral (≥4 gracias alta, <4 honestidad) y transiciona a sugerencia.
  • Sugerencia: showSuggestionUI con input y botón; window.handleSuggestion envía API.saveInteraccion con {rating, sugerencia} y muestra toast de confirmación; el texto libre escrito durante la fase de sugerencia se inserta en el input.
  • Re-render bilingüe: listener de fe:idioma actualiza etiquetas de calificación y placeholder de sugerencia.

5.4 Reporte mensual y CRM (js/report.js)

Reporte: buildMonthOptions (12 meses YYYY-MM con nombres localizados con locale es-CO/en-US), generateReport controla estados (generando/lista), maneja mes vacío (reportEmpty), y render(list) calcula los tres bloques: (a) animateCounter de personas atendidas; (b) promedio con un decimal, estrellas visuales (redondeo Math.round), % satisfacción y barras de distribución con colores por severidad y ancho mínimo 8%; (c) lista de sugerencias con estrella repetida y tarjetas de recomendaciones.

Motor de recomendaciones: 11 reglas (umbrales 4,5 y 3,5; satisfacción < 80%; 9 grupos de palabras clave: entregas, precios, variedad, digital, suscripciones, pagos, cumplimiento, ocasiones, fidelización; fomento si < 5 sugerencias; celebración si promedios excelentes sin otras reglas).

CRM: renderClientes consume API.getClientesAdmin; calcularEdad deriva la edad (clamp 0-129); sem(v) muestra puntos suspensivos salvo mostrarSemiprivados (control de alternancia); protegido() genera el marcador con candado para preferencias/identificación/pago; encabezados con chips PÚB/SEM/SEN. Los eventos fe:idioma y fe:moneda regeneran tabla y reporte.

7. Control de versiones y gestión del código

7.1 Prácticas aplicadas

  • Control de versiones Git (repositorio local), con commits por módulo y mensajes descriptivos.
  • No se versionan binarios innecesarios; las imágenes y vendor son componentes estáticos del despliegue.
  • El README del repositorio documenta estructura, puesta en marcha, cuentas demo, requisitos cubiertos y cómo conectar un backend alternativo.

7.2 Buenas prácticas de calidad (revisión de código)

  • Revisión por pares antes de integrar cada módulo, con checklist de: separación de capas, validaciones de entrada, parametrización de consultas, manejo de errores y mensajes bilingües.
  • Verificación de consistencia entre los textos ES/EN (ambos idiomas presentes en I18n.te).
  • Verificación de que ninguna consulta SQL se construya por concatenación de datos del usuario.
  • Se corrió el sitio bajo phpMyAdmin para validar que las tablas, índices y restricciones quedaron según el diseño.

8. Hallazgos de desarrollo y su resolución

IDHallazgoImpactoResolución
HD-01Al abrir el sitio con doble clic (file://) el fetch hacia PHP falla silenciosamente.Alto (experiencia)api.js detecta protocol file: y muestra error explicativo pidiendo usar http://localhost.
HD-02Posible condición de carrera al descontar inventario en pedidos simultáneos.Alto (integridad)Se implementó SELECT ... FOR UPDATE dentro de una transacción; el segundo pedido con stock agotado recibe error claro.
HD-03La fecha de nacimiento cruda podía filtrarse al panel si se agregaba al clientes.php.Alto (privacidad)El CRM solo calcula y muestra la edad; advertencia en comentarios del código.
HD-04Los textos de la versión inglesa podían quedar sin traducción en componentes dinámicos.MedioMecanismo evento fe:idioma + uso disciplinado de I18n.te en todo render dinámico.
HD-05El catálogo semilla del frontend se desincronizaba con la BD al editar productos.MediocargarCatalogo muta Data.productos (length=0 + push) preservando referencias de chatbot y carrito.
HD-06El mes sin datos del reporte mostraba métricas en cero confusas.BajoDiseño de estado vacío (reportEmpty) con mensaje y nombre del mes.
HD-07Inconsistencia de año en pies de página (index 2025 vs cliente 2026) y README con secciones duplicadas.Bajo (higiene)Registrado para corrección en mantenimiento; documentado en la fase de pruebas (defectos).
